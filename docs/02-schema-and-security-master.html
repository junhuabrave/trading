Message schema, security master and snapshot format

The contract every component of the trading stack speaks. One schema file generates the C++ hot path, the Go services, the Python research code and the TypeScript client; the security master and its daily snapshot are defined in the same file.

The bar we are aiming at

The large banks did not design their trading stacks; they accumulated them. Inside Morgan Stanley, JPMorgan or Goldman there are dozens of order formats, several position systems that disagree with each other at 4pm, and reference data that arrives by six different routes. Their edge is capital, client relationships and decades of venue certification, not schema discipline. That is the opening. A stack where every message, every reference record and every strategy parameter is one generated type, sequenced on one log, is something they would build if they could start again, and cannot.

The schema is therefore where speed, resilience, observability and strategy flexibility are all decided at once:

  • Speed: fixed-layout binary, decoded by pointer cast, no parsing, no allocation, every hot field on the first cache line.
  • Resilience: every message carries its sequence number, its cause and its origin time, so any state can be rebuilt and any decision replayed.
  • Observability: causality and timestamps are in the header, not bolted on; latency and audit are queries over the log.
  • Strategy flexibility: strategies are consumers of the same messages with their own parameter messages; a new strategy never touches the schema of the core.
  • Scalability: partitioned logs with watermarks keep determinism when one sequencer is no longer enough.

One schema, four languages

Encoding: Simple Binary Encoding (SBE), the FIX Trading Community standard used by CME, B3 and the Aeron ecosystem. It is open source (Apache 2.0), it produces flyweight codecs that read fields directly from the buffer with no copying, it has first-class schema versioning with append-only extension, and it has maintained generators for C++, Java, Go, Rust and C#. FlatBuffers and Cap'n Proto were the alternatives; SBE wins on decode cost (no vtable or pointer indirection for fixed fields) and on being designed for exactly this use.

The single source of truth is schema/trading.xml. The build generates:

  • C++23 header-only codecs for the hot path (SBE's generator, with our own thin wrapper adding constexpr size checks and struct-of-arrays helpers).
  • Go codecs for control-plane and cold-path services.
  • Python codecs for research, TCA and the simulator driver, plus a generated Arrow schema so a day's log converts to Parquet with one function.
  • TypeScript type definitions and a JSON projection for the web client and for humans reading messages in tooling.
  • Documentation: every message and field, with its version history, generated into this document's successor.

Nobody writes a message struct by hand in any language. A pull request that changes the schema runs the compatibility checker (below) and the full simulator replay before it merges.

All messages are little-endian, 8-byte aligned, and padded to a multiple of 16 bytes. Fields are ordered so that the ones the hot path reads first sit in the first 64 bytes after the header.

Frame header and causality

Every message on every log starts with the same 48-byte header. Three fields do most of the work: seq is where the message sits in total order; causeSeq is the sequence number of the message that caused this one; originTs is when the event first touched our hardware. Together they give a complete causal graph of the day.

Follow causeSeq backwards from a fill and you reach the venue ack, the child order, the router decision, the risk accept, and the client's original order, each with a timestamp. That chain is the latency breakdown for that order, the audit trail for a regulator, and the evidence for a client dispute, and it costs eight bytes per message.

Versioning rules

SBE's extension model, enforced by a checker in CI:

  • Fields are append-only. A new field gets sinceVersion and a default; old readers never see it, new readers decoding old messages get the default.
  • Template ids, field ids and enum values are never reused. Deprecated ones are marked and stay in the schema forever.
  • A field's type never changes. If a type is wrong, add a new field and deprecate the old one.
  • Schema version is a single integer, bumped on any change. Every log records the version each message was written with.
  • A new engine must decode every historical log since day one. The CI job replays a sample day from each past schema version.
  • The wire header itself (48 bytes) is version 0 and never changes. Anything we later need in the header goes in a message, not the header.

Log topology and scale

One sequencer handles tens of millions of messages per second, which is more than enough for orders, fills, risk and reference: the core stream. Market data is the scale problem. US equities direct feeds run a few billion messages a day with bursts above a million per second at the open; options (OPRA) is an order of magnitude more. Sequencing all of it through the core stream would either saturate the sequencer or force the core log to carry data most consumers do not need.

The rule: market data lives on its own sequenced streams, partitioned by symbol range (so a symbol's data from every venue is on one stream and book building is local). The core stream carries everything else. Any hot-path message that depends on market state carries an MdWatermark: the (stream, seq) pairs it had consumed when it decided. Replay reconstructs precisely the book each engine saw, and the design shards horizontally by adding streams. The same rule lets a market-making engine for symbols 0 to 3999 run on a different host from the one for 4000 to 7999 with no shared state.

Account-level state (buying power, exposure) is on the core stream and is not sharded; a single risk engine at one microsecond per order handles millions of orders a day. If that ever binds, risk shards by account range, and the router's child orders for one parent stay on one shard.

Security master data model

The origin system is a PostgreSQL database owned by the security master service. Every table is bitemporal: valid_from/valid_to (when the fact is true in the world) and recorded_at (when we learned it), so "what did we believe about AAPL's tick size at 10:14 on the 3rd" is a query. The published artefacts are the snapshot and the sequenced updates; nothing on the trading floor queries the database.

Nightly pipeline

  1. Ingest each source into a staging table with the raw file hash recorded. Sources: exchange symbol files, SIP end-of-day, vendor descriptive feed, CUSIP file, OpenFIGI resolution, DTCC corporate actions via the clearing firm, vendor corporate actions, SRO threshold lists, stock-loan ETB/HTB output, compliance restricted list, fee schedules, calendars.
  2. Resolve into the bitemporal master by precedence; every conflict written to a review table with both values.
  3. Assign indexes for any new instrument; indexes are allocated from a monotonic counter and never recycled.
  4. Apply corporate actions with tomorrow's ex-date: splits adjust reference prices and lot data, symbol changes create a new listing on the same index, delistings set status.
  5. Validate: symbol count within 2% of yesterday, no duplicate identifiers, every symbol that traded yesterday still present or explicitly delisted, tick tables valid, every corporate action with a today ex-date in Applied state, two-source agreement on corporate actions, index continuity. Any failure blocks publication and pages the on-call.
  6. Publish the snapshot file: build, hash with BLAKE3, write to the distribution store, and emit the snapshot manifest. The control plane refuses to start the trading day without a manifest whose validation status is green.
  7. Diff tool: given two snapshot versions, emit the difference as a series of SymbolUpdate, ListUpdate, CorporateAction messages. This is how an intraday correction is delivered, and it is how a late-night republish is delivered to engines that already loaded the earlier version.

Snapshot binary layout

The snapshot is one file, memory-mappable, page-aligned, with fixed-size records in every section so any record is found by arithmetic. It is defined in the same SBE schema as the messages (the record types are SBE composites), so the generated codecs read it directly.

How engines load it

  1. Control plane publishes today's manifest (path, version, hash). Engines will not start without it.
  2. Engine mmaps the file read-only, verifies magic, format version, schema version compatibility and the BLAKE3 content hash.
  3. Engine copies the fields it uses into its own struct-of-arrays: for the risk engine, a uint32 flags[], int64 refPrice[], uint16 tickTable[]; for the market maker, ADV and lot size as well. Copying is deliberate: the engine's arrays are then written by sequenced updates without touching the mapped file, and the file remains the pristine record of what was loaded.
  4. Engine subscribes to the core stream from the beginning of the day (or from its last checkpoint) and refuses to process past SessionStart unless the message's snapshot hash equals the one it loaded.
  5. Reference update messages are applied inline on the engine's thread as they arrive in sequence: a ListUpdate is one bit operation; a SymbolUpdate writes the selected fields; a SymbolAdd copies a full record into a preallocated slot.
  6. Checkpoints (every N seconds, sequenced) let a restarting engine load the snapshot, then apply only the messages since the last checkpoint, rather than replaying from the open.

Strategy framework

Flexibility for strategy design comes from a strict interface, not from a loose one. A strategy is a deterministic object that consumes messages and produces intents. It never touches a socket, a clock, or a file. Everything it knows arrives as messages; everything it wants to do leaves as messages; the framework handles the rest.

// Every strategy implements this. The framework calls it in sequence order,
// single-threaded, with no allocation permitted after init().
class Strategy {
public:
  virtual void init(const StrategyContext& ctx,
                    const RefDataView& ref) = 0;        // snapshot views, params
  virtual void onBook(const BookView& book, SymIdx s) {}
  virtual void onTrade(const Trade& t) {}
  virtual void onNbbo(const Nbbo& n) {}
  virtual void onFill(const ExecReport& er) {}
  virtual void onOrderState(const OrderState& os) {}
  virtual void onPosition(const PositionView& p, SymIdx s) {}
  virtual void onParam(const StrategyParam& p) {}      // sequenced, replayable
  virtual void onTimer(Ts now, uint32_t timerId) {}    // timers are log messages too
  virtual void onRef(const RefUpdate& r) {}
  virtual void onKill() = 0;                           // must flatten deterministically
  // Output: strategies write intents; the framework converts them to
  // NewOrder / Cancel / QuoteIntent and stamps causeSeq.
protected:
  Intents& out();
};
  • Parameters are messages. StrategyParam (strategyId, paramId, value as int64 or fixed-point) is sequenced, so a parameter change is an event in the log with a time and a cause, and replay reproduces the strategy's behaviour before and after it. Research fits parameters in Python and publishes them through the control plane; the live engine has no learning code.
  • Timers are messages. A strategy asks for a timer; the framework sequences a Timer message when it fires. Replay sees the same timer at the same sequence position, so "what would this strategy have done" is answerable exactly.
  • Signals are messages. A signal computed by one component (toxicity score, borrow-rate change, microprice from a model) is published as Signal (signalId, symbolIdx, value) and consumed by any strategy. New signals never change the core schema.
  • Same binary in simulation and production. The simulator feeds recorded or synthetic streams; the strategy cannot tell. A strategy is promoted by running it against the last 60 recorded days in CI, comparing its intents to a stored baseline, and reviewing the diff.
  • Hot deployment without a stop. Start the new strategy instance in shadow mode: it consumes the live log and writes intents to a shadow stream that the framework drops. When its state is caught up, a sequenced StrategyStart switches the live intent stream to the new instance and a StrategyStop retires the old one, at the same sequence number, so there is no window where both or neither are live.
  • Sandboxing. Strategy code runs in the engine process for latency, so its safety comes from the interface (no I/O possible), from the risk engine downstream (every intent still passes risk), and from per-strategy limits (InventoryLimit, message rate, max notional) enforced by the framework before the intent becomes an order.

Observability in the schema

  • Per-message latency is the difference between originTs and seqTs, and between an effect's seqTs and its cause's. No instrumentation needed; a Python one-liner over the log gives the p99.9 for any stage on any day.
  • Telemetry stream. Components write LatencySample (stage, histogram bucket counts per second) and QueueDepth to a separate stream that is not sequenced with the core log, so telemetry can never slow trading. An exporter turns it into Prometheus metrics for Grafana; alerting is on percentiles, not means.
  • Causal tracing. The causeSeq chain is exported per order to a trace viewer (OpenTelemetry format) so an engineer sees the order's life as a waterfall with real timestamps.
  • Business metrics from the same log: fill rate, reject reasons, quote uptime per symbol, inventory, price improvement per internalised fill, locate grant rate, all computed by cold-path consumers with no extra instrumentation in the hot path.
  • Determinism check as a metric. The standby engines compare their state hash to the primary's at every checkpoint. A divergence is a page; it means non-determinism has crept in and the replay guarantee is at risk.

Resilience

  • Sequencer. Primary journals to NVMe before fan-out; standby consumes the fan-out and journals independently; promotion resumes from the last durable sequence. Aeron Cluster provides this pattern with Raft consensus if we want a multi-node log rather than primary/standby; the choice is a deployment decision, not a schema one.
  • Idempotency. Every inbound external event carries an idempotency key (venue exec id, client clOrdId with session); the gateway drops duplicates before sequencing, and the OMS drops a duplicate fill by exec id if one slips through.
  • Gap handling. Consumers detect a sequence gap and request replay from the sequencer's archive; they never process past a gap. Market-data streams do the same against their own archives.
  • Checkpoints. Sequenced Checkpoint messages mark points where every engine writes its state hash; a restart loads the snapshot, applies from the last checkpoint, and verifies the hash before going live.
  • Kill switch. One sequenced message; every engine cancels all open orders and pulls all quotes at the same sequence number, and the venue gateways send cancel-on-disconnect regardless.
  • Schema-level safety. No message can be interpreted two ways: fixed layout, explicit versions, reserved fields zero.

Aeron and SBE are the two that shape the code. They come from the same authors, they are designed to be used together, and they are the basis of several production exchanges and clearing systems. Adopting them means our sequencer is Aeron Archive with our ordering logic on top, our IPC is Aeron shared-memory, and our messages are SBE. The one thing we still write ourselves is the single-writer ordering core and the watermark logic, which is a few thousand lines and the part that must be ours.

First code

The natural first deliverables, in order, each with tests that run in CI:

  1. schema/trading.xml with the control, order, market-data and reference families, the FrameHeader, and the snapshot record composites; the codegen wired into the build; the compatibility checker.
  2. tools/snapshot: build a snapshot from a CSV fixture, verify it, diff two snapshots into messages. This exercises the record layouts before any engine exists.
  3. core/refdata: the loader, the struct-of-arrays views, and the update appliers, with a test that loads a snapshot, applies a day of synthetic reference updates, and matches the resulting state to a snapshot built for the next day.
  4. core/seq: the ordering core over Aeron, the journal, the watermark, and a determinism test: two consumers replay the same log and hash to the same state.
